# Detailed Design

## 1. Domain types

```ts
export type ProjectPermissionPreset = "inspect" | "design" | "develop";
export type ProjectSource = "manual" | "discovered";
export type ProjectAvailability = "available" | "missing" | "not_allowed" | "invalid";
export type WorkspaceMode = "checkout" | "worktree";

export interface RegisteredProject {
  id: string;
  slug: string;
  name: string;
  root: string;
  rootKey: string;
  permissionPreset: ProjectPermissionPreset;
  defaultMode: WorkspaceMode;
  pinned: boolean;
  source: ProjectSource;
  createdAt: string;
  updatedAt: string;
  lastOpenedAt?: string;
}

export interface ProjectView extends Omit<RegisteredProject, "rootKey"> {
  availability: ProjectAvailability;
  unavailableReason?: string;
}
```

Opaque IDs use `prj_${randomUUID()}`. Slugs are human-readable but not identity.

## 2. Database migration

Add the next append-only migration after current version 3.

```sql
create table if not exists registered_projects (
  id text primary key,
  slug text not null unique,
  name text not null,
  root text not null,
  root_key text not null unique,
  permission_preset text not null default 'develop',
  default_mode text not null default 'checkout',
  pinned integer not null default 0,
  source text not null default 'manual',
  created_at text not null,
  updated_at text not null,
  last_opened_at text
);

create index if not exists registered_projects_pinned_last_opened_idx
  on registered_projects(pinned desc, last_opened_at desc, name asc);
```

Add nullable `project_id` to `workspace_sessions` using the existing `addColumnIfMissing` pattern. Do not add a foreign key through `ALTER TABLE`; restoration must tolerate a forgotten project.

Drizzle schema must match migration storage types.

## 3. Path canonicalization

`canonicalizeProjectRoot(input, allowedRoots)`:

1. expand `~`,
2. resolve absolute path,
3. `stat` and require directory,
4. `realpath`,
5. `assertAllowedPath(realPath, allowedRoots)`,
6. produce:
   - `root`: canonical real path,
   - `rootKey`: normalized comparison key.

`rootKey`:

```ts
const normalized = normalize(realPath);
return process.platform === "win32" ? normalized.toLocaleLowerCase("en-US") : normalized;
```

Do not follow a user-provided symlink to an outside target; `assertAllowedPath` runs on the real target.

## 4. Slug generation and selector resolution

Slug normalization:

- lowercase,
- Unicode NFKD,
- letters/digits retained,
- whitespace and separators become `-`,
- repeated dashes collapsed,
- empty result becomes `project`,
- collision suffix `-2`, `-3`, and so on.

Selector priority:

1. exact opaque ID,
2. exact slug,
3. exact case-insensitive display name only when unique.

Partial/fuzzy matching may be used only to populate error suggestions, never to select.

## 6. Discovery algorithm

Input:

```ts
interface DiscoveryOptions {
  roots?: string[];
  maxDepth?: number;       // default 4
  maxDirectories?: number; // default 5000 per scan
  timeoutMs?: number;      // default 10000
  concurrency?: number;    // default 16
}
```

Rules:

- roots must be a subset of configured allowed roots,
- breadth-first traversal,
- no symlink/reparse following,
- stop descending when `.git` directory or `.git` file is found,
- skip heavy names,
- check abort deadline between batches,
- return partial result with `truncated` and `reason`,
- return candidates sorted by root then relative path,
- no persistence during scan.

Avoid synchronous recursive filesystem APIs on the event loop.

## 7. Dashboard configuration

Extend user config:

```ts
  dashboardPort?: number;

```

Extend auth config:

Runtime defaults:

- host: hardcoded `127.0.0.1`
- port: configured value or MCP port + 1, with validation

Environment overrides:

- `DEVSPACE_DASHBOARD=0|1`
- `DEVSPACE_DASHBOARD_PORT=<port>`

The admin host is not configurable to a non-loopback address in the initial implementation.

## 8. Dashboard authentication

Bootstrap flow:

1. `devspace dashboard` reads `dashboardToken`.
2. It opens:
   `http://127.0.0.1:<port>/#token=<urlencoded-token>`
3. Dashboard JavaScript reads the fragment.
4. It copies the bootstrap token to tab-scoped `sessionStorage` and immediately
   calls `history.replaceState` to remove the fragment before awaiting network.
5. It POSTs the token to `/api/session`.
6. Server validates with constant-time comparison.
7. Server creates an in-memory random session ID and CSRF token with an expiry.
8. Server sets an HttpOnly `SameSite=Strict` session cookie.
9. Client stores the CSRF token only in memory.

On reload, `GET /api/session` returns the CSRF token only when the HttpOnly
session cookie remains valid. If the in-memory server session was lost after a
restart, the same tab may recreate it with the `sessionStorage` bootstrap token.
An authenticated API request retries at most once after shared single-flight
reauthentication. Invalid bootstrap credentials clear both the tab token and
the in-memory CSRF value. Session/bootstrap responses use `Cache-Control:
no-store`.

Every mutation API requires:

- valid session cookie,
- exact local Host header,
- exact local Origin,
- `X-DevSpace-CSRF`,
- JSON content type where applicable.

No CORS headers are added.

## 9. Admin API

All responses use a typed envelope:

```ts
type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: string; message: string; details?: unknown } };
```

Routes:

```text
POST   /api/session
DELETE /api/session
GET    /api/status
GET    /api/projects
POST   /api/projects/scan
POST   /api/projects
PATCH  /api/projects/:id
DELETE /api/projects/:id
GET    /api/projects/:id/git-status
POST   /api/folder-picker
GET    /api/agents?projectId=<id>
```

`DELETE /api/projects/:id` means forget metadata. It never invokes filesystem removal.

Git status is requested separately and timeout-bounded.

## 10. Native folder picker

Primary project onboarding is scan/import or manual path. The native picker is a convenience adapter.

```ts
interface FolderPicker {
  isSupported(): Promise<boolean>;
  chooseDirectory(options?: { initialDirectory?: string }): Promise<string | undefined>;
}
```

Windows implementation:

- spawn a fixed `powershell.exe` command with `-NoProfile -STA -EncodedCommand`,
- fixed script uses `System.Windows.Forms.FolderBrowserDialog`,
- no user-controlled executable/script fragments,
- stdout contains only selected path,
- cancellation returns `undefined`,
- timeout and child cleanup applied.

The selected path is not trusted until normal canonicalization and allowlist validation.

Other platforms return unsupported until a tested native adapter exists. Dashboard shows manual path input.

## 11. Workspace association

Extend workspace model:

```ts
interface Workspace {
  // existing fields
  projectId?: string;
  project?: Pick<ProjectView, "id" | "slug" | "name" | "permissionPreset">;
  policy: WorkspacePolicy;
}
```

`WorkspaceRegistry` constructor receives `ProjectRegistry`.

For every checkout open:

1. canonicalize/assert as today,
2. query project by canonical path key,
3. choose registered policy or legacy policy,
4. persist project ID in workspace session.

For worktree open:

- lookup project using source root,
- policy follows the source project,
- workspace root remains the managed worktree path.

Restoration:

- use stored `projectId` when present,
- revalidate source/root,
- if project was forgotten, use legacy policy only if current path remains allowed,
- if project still exists, use current project preset, not a stale serialized copy.

## 12. Policy guard

```ts
type WorkspaceOperation =
  | "read"
  | "search"
  | "list"
  | "write"
  | "edit"
  | "patch"
  | "artifact_write"
  | "shell"
  | "delegate_read_only"
  | "delegate_write"
  | "delegate_full_access";

interface WorkspacePolicyGuard {
  assertOperation(workspace: Workspace, operation: WorkspaceOperation): void;
  assertWritePath(workspace: Workspace, relativePath: string): void;
  assertPatchPaths(workspace: Workspace, paths: PatchAffectedPath[]): void;
}
```

Design path rule:

- allow `docs/**`,
- allow root-level `.md` and `.mdx`,
- allow `.devspace/**`,
- deny secret-like names and `.env*` regardless of extension,
- deny paths outside workspace through existing resolver.

The operation decision returns one required scope: `no-policy-path`, `workspace-scope`, or `design-documentation-scope`. It does not accept an optional path or partially authorize paths; canonical path authorization is a separate mandatory guard step for path-bearing operations.

`delegate_full_access` is explicit so callers cannot interpret an unknown/undefined operation as authorization not being required. Registered `inspect`, `design`, and `develop` deny it. Legacy unregistered workspaces retain existing behavior explicitly for compatibility.

Do not classify arbitrary shell strings as “read-only.” A preset either allows shell or denies it.

## 13. MCP tool schemas

### `list_projects`

Input:

```ts
{
  includeUnavailable?: boolean;
  pinnedFirst?: boolean;
}
```

Output:

```ts
{
  result: string;
  projects: ProjectView[];
  summary: {
    total: number;
    available: number;
    unavailable: number;
  };
}
```

Annotations: read-only, non-destructive, closed world.

### `open_project`

Input:

```ts
{
  project: string;
  mode?: "checkout" | "worktree";
  baseRef?: string;
}
```

Output is the `open_workspace` output schema plus:

```ts
{
  project: {
    id: string;
    slug: string;
    name: string;
    permissionPreset: ProjectPermissionPreset;
    defaultMode: WorkspaceMode;
  };
}
```

If `mode` is omitted, use project default.

### `exec_command` verification association

The existing command tool retains its current required inputs and accepts one
optional verification association:

```ts
{
  verification?: {
    agentId: string;
    type: "typecheck" | "tests" | "build";
  };
}
```

The target must be a completed result-available local-agent run in the same
workspace. The caller identifies the check category and target but cannot
submit an outcome. `ProcessSessionManager` remains the command/exit owner; its
observed exit code and signal produce passed/failed evidence through the
operation verification projector. Commands, arguments, output, prompts, and
provider text are not copied into evidence. Omitting `verification` preserves
the existing command behavior and response contract.

### Agent tools

`delegate_task` input:

```ts
{
  workspaceId: string;
  target?: string;
  goal: string;
  context?: string;
  relevantFiles?: string[];
  acceptanceCriteria: string[];
  rules?: string[];
  verification?: string[];
  sourceDocuments?: string[];
  model?: string;
  thinking?: string;
}
```

`get_agent_status` input: `{ id: string }`

`list_agents` input: `{ workspaceId: string }`

`continue_agent` input:

```ts
{
  id: string;
  prompt: string;
  model?: string;
  thinking?: string;
}
```

Tools are absent when subagents are disabled.

## 15. Local agent service extraction

Move reusable behavior from `src/cli.ts` into `LocalAgentService`.

The service receives:

- config,
- local-agent store,
- profile loader,
- provider availability checker,
- provider runner,
- worker spawner,
- clock/temp-file adapter for tests.

CLI commands call the service and format terminal output. MCP tools call the same service and create structured results/cards.

The worker deletes the temporary prompt file and its temporary directory in `finally`.

## 16. MCP Apps UI

Extend `ToolName` with:

- `list_projects`
- `open_project`
- `delegate_task`
- `get_agent_status`
- `list_agents`
- `continue_agent`

Add card fields for projects and agent records.

Project list card behavior:

- render pinned/available projects first,
- show name, slug, mode, preset, availability,
- Open Checkout and Open Worktree actions,
- use `app.getHostCapabilities()?.serverTools` before `callServerTool`,
- render loading/error/result state locally,
- after successful open, call `updateModelContext` when supported,
- otherwise offer `sendMessage`,
- preserve existing card render paths.

Do not assume the app is a full-page dashboard. It remains a tool-result card.

## 17. Vite build

Use a multi-entry build:

- existing MCP App entry,
- new dashboard entry.

Manifest lookup for the MCP App must remain stable. Dashboard assets are served only by the local admin app.

## 18. Logging and redaction

Log:

- project ID/slug,
- operation,
- success/failure,
- duration,
- sanitized error code.

Do not log:

- dashboard bootstrap token,
- admin session/CSRF values,
- OAuth tokens,
- full handoff context by default,
- native picker script or environment,
- file contents.

Paths may be logged according to existing DevSpace policy, but token-bearing URLs must never be logged.

## 19. Shutdown

`serve()` starts MCP listener first and dashboard listener second.

Shutdown order:

1. stop accepting dashboard requests,
2. stop accepting MCP requests,
3. close MCP sessions/process sessions,
4. close stores,
5. close both HTTP servers,
6. exit.

Dashboard startup failure does not leave a half-created listener or unhandled promise.

## 20. Live Operations and Control Center UI refinement

The provider-neutral run, event, evidence, retention, SSE, reconnect, and stop contracts are defined canonically in `11_LIVE_OPERATIONS_DASHBOARD.md`.

The visual tokens, density, component states, accessibility, motion, and prohibited visual patterns are defined canonically in `12_UI_VISUAL_DESIGN_SYSTEM.md`.

The Projects, Project detail, Runs, live run, Agents, System, overlay, loading, error, disconnected, and responsive screen contracts are defined canonically in `13_UI_SCREEN_SPECIFICATIONS.md`.

Implementation rules:

- instrument existing owners through narrow adapters; do not duplicate file, process, or agent execution,
- keep run state separate from assurance stage,
- use append-only SQLite migrations and bounded payloads,
- expose operation snapshots, SSE, and capability-based stop only through the authenticated loopback admin server,
- preserve public MCP tool schemas unless an accepted requirement explicitly changes them,
- build shared dashboard tokens/shell before migrating one complete screen slice at a time,
- reuse pure formatting, ANSI, diff, patch, and review helpers where compatible,
- do not force dashboard and MCP App cards into one component tree when host constraints differ,
- reconcile the design with current code and installed provider SDK types in the first GOAL_06 Micro Work Unit before finalizing TypeScript DTOs or migrations.

## 21. Codex-parity context, review, and outcome contracts

The canonical DTOs, bounds, data flows, failure modes, complexity receipts,
parity cases, and work-unit order are defined in
`goals/GOAL_08_CODEX_PARITY.md`.

Implementation constraints:

- add `repositoryContext` only as a failure-isolated projection after the
  existing workspace is opened;
- derive branch, `HEAD`, dirty paths, and file operations from the existing
  repository-diff owner;
- derive the tree fingerprint through an isolated temporary Git index and
  share that primitive with review checkpoints and verification evidence;
- read only workspace-root `package.json` script names; do not infer monorepo
  packages or recommended commands;
- preserve the existing `show_changes` text and card payload while adding a
  separately bounded structured review bundle for the model;
- validate an optional review `agentId` against both workspace ID and canonical
  root before advancing the review checkpoint;
- add the verification basis fingerprint as nullable evidence metadata in the
  existing operation SQLite owner; legacy evidence remains
  `unknown_legacy`;
- use Codex SDK `outputSchema` for `completed | needs_input`; do not parse prose
  markers and do not apply the contract to providers without an equivalent
  native schema;
- persist disposition and one bounded question in the existing local-agent
  row, separate from execution status;
- project `needs_input` as waiting/blocked work and return to running when
  `continue_agent` resumes the same provider session;
- expose only optional `waitMs` on `get_agent_status`; keep poll cadence an
  internal service detail and never restart or cancel on timeout.
